# 絵画ドリル 設計ドキュメント

> 「絵画・宗教・哲学を学びながら英語を学ぶ」という発想の第一弾として、絵画に絞って設計を固めた記録。宗教・哲学は一旦保留（後述）。実装はまだ未着手で、次は DB スキーマと fact-base の執筆。

## 1. 背景・動機

README の産出仮説・生成効果・弱点プールという既存コンセプトはそのままに、コンテンツドメインを広げたい。絵画・宗教・哲学は「乗り物」であり、狙いは英語産出の語彙・構文の天井を日常描写より引き上げること（構図・象徴・技法などの抽象語彙）。

宗教・哲学も検討したが、まずは絵画一本に絞る。理由：

- 絵画は既存の①画像描写ドリルの延長で作れる（画像→英語産出→AI添削、のメカニクスがそのまま使える）
- 宗教・哲学はテキスト起点の新フォーマットが必要で、かつ「内容理解の欠如」と「英語力の欠如」を弱点プール上で混同するリスクがあり、設計がもう一段複雑

## 2. フロー設計

Duolingo的な「読んで終わり」の罠（README冒頭で否定しているゲーミフィケーションの罠と同根）を避けるため、AIの解説を必ず次の産出のきっかけに変換する2ラウンド構成にした。

1. **Round 1（先入観ゼロの一次反応）**
   絵画を見せる（タイトル・作者は非表示）→「何が見える／何を感じるか」を英語で自由記述 → AI1（既存の添削役）が文法・語彙を添削し、弱点プールに投入。既存①のフローと同一。

2. **Reveal（解説）**
   AI3（新設・キュレーター役）が、事実ベースで保存された fact-base と、ユーザーの Round1 回答を突き合わせてパーソナライズされた解説を生成する。「あなたが気づいた〇〇は美術史家も指摘している点」「△△（構図/象徴/技法）は見落としがち」という応答形式にし、単なる知識ダンプにしない。

3. **Round 2（必須・情報を得た後の再産出）**
   解説を読んだ上での再反応を英語で書かせる（**スキップ不可**）→ AI1が添削、弱点プールに再投入。Revealで出てきた新語彙（symbolism, allegory, patron, composition等）を使わせることで、Round1で出せなかった語彙の生成効果を二重にする。

コスト面：セッションあたりAI1が2回（Round1・Round2）、AI3が1回呼ばれる。既存①より呼び出し回数が増えるが、産出仮説への忠実さを優先し許容する判断済み。

## 3. AIの役割分担（README への追記案）

既存の AI1（添削役）・AI2（辞書相棒、無文脈）に加えて、**AI3（キュレーター役）**を新設する。

- AI3は事実を自分で生成しない。DBに保存済みの fact-base を土台に、ユーザーの回答に応じて提示内容を組み立てるだけ。歴史的事実の捏造リスク（英語添削の間違いと違い、事実の間違いはユーザーの信頼を直接損なう）をここで断つ。

## 4. コンテンツDB（カリキュラム型・非ランダム）

絵画は情報量（記録が残っている背景・解釈の厚み）に作品ごとの差が大きいため、ランダム出題ではなく事前に厳選したセットを用意する。1枚ごとに以下を用意：

- 基本情報（作者・年代・様式）
- 事実ベースの背景（依頼主、制作経緯、技法）
- 作者の意図（学術的裏付けのあるもの）
- 知られている解釈群（複数。単一の「正解」にしない）
- **注目要素リスト**（構図・象徴・技法上の見どころの箇条書き）→ Round1回答との突き合わせに使い、「気づけた/見落とした」の判定材料にする

## 5. MVP絵画リスト（確定・6枚）

1. サン＝ベルナール峠を越えるボナパルト
2. デラウェア川を渡るワシントン
3. ネルソン提督の死（アーサー・ウィリアム・デヴィス版）
4. ナポレオンの戴冠式
5. 1808年5月3日、マドリード
6. 民衆を導く自由の女神

選定基準：有名・背景がシンプル・解釈がシンプル。「史実 vs 神話化（英雄がどう演出/神話化されるか）」という軸が緩く貫かれた結果になっている。

**検討したが外した/差し替えた項目：**

- 十字架降下（宗教画）→ 除外。「宗教・哲学は一旦保留」の方針と矛盾するため
- トラファルガーの海戦（一般的な海戦画）→ ネルソン提督の死（デヴィス版）に差し替え。海戦画は船・煙・海で画面が埋まり焦点が定まらず、Round1の気づき出しが散漫になる懸念があった。デヴィス版は目撃者証言を基にした船内描写で焦点が明確、かつベンジャミン・ウェスト版（甲板上での英雄的演出）との対比で「史実 vs 神話化」の題材としても深掘りしやすい
- 肖像画などジャンルを分散させる7枚目（例：真珠の耳飾りの少女）→ 見送り。6枚は歴史画に統一されており fact-base の執筆パターンを作りやすい。ジャンルの多様化は次バッチで検討

## 6. UI/UX設計

### 6.1 ルート構成：新設（既存①は流用しない）

既存の `/practice/describe` は「1ラウンド完結」前提でページ全体が組まれており、「Round1→Reveal→Round2必須」の3段階フローを条件分岐で押し込むと既存①のシンプルさを壊す。ドリル種別ごとに別ルートという既存方針（`practice/diary`, `practice/topic` も別ルート）とも合致するため、新設ルート（例: `/practice/painting`）とする。

一方でロジックは流用する：

- `lib/ai1.ts` の添削エンジン（`gradeDescription`）→ Round1・Round2どちらも「画像を見て書いた英文を添削する」という点で既存①と同タスクなのでそのまま使える
- `toConceptKey` 経由の弱点プール書き込み → テキスト非依存なので無改造で使える
- `lib/credits.ts`（consumeCredit/refundCredit）、rate-limit、concurrency lock → そのまま
- `ResultModal` のUI → 共通コンポーネント化して両ドリルで共有

### 6.2 クレジット消費：セッション買い切り・返金は技術的失敗時のみ

- 絵画の取得自体はUnsplash APIのような外部レート制限のかかるAPIではなく自前DB参照なので、取得コストは0（既存の `nextImage` コストはUnsplash API保護のための設計であり、この文脈では不要）
- Round1添削・Round2添削は既存の `grade`（デフォルト3）を流用。Reveal（AI3生成）はfact-baseとRound1回答のテキスト合成が中心で画像の再解析は必須ではないため、`grade`より軽い新コスト区分を新設（例：`question`と同じ1、または中間の2）
- **Round1送信時に「grade + reveal + grade」の合計コストを一括で消費**（セッション買い切り）。既存①は各アクションごとに `consumeCredit` するが、絵画ドリルはRound2必須の直線的な構造なので、Round2の途中でクレジット不足になり詰む事態を防ぐため一括消費にする
- **返金ポリシー**：ユーザーが途中離脱した場合（Round1だけでRound2をやらない等）は返金しない。一方、AI呼び出し自体が技術的に失敗した場合の `refundCredit`（既存 `app/api/grade/route.ts` にあるパターン）は維持する。ユーザーの落ち度でない障害からユーザーを守る仕組みとクレジット買い切りポリシーは別軸

### 6.3 カリキュラムUI：自由方式＋段階制（ステージ）

README冒頭で明確にストリーク/バッジ的なゲーミフィケーションの罠を否定しているため、演出的な進捗ではなく「実際に何枚学んだか」を素直に示す進捗表示にする。

- 絵画に `tier`（ステージ番号）を持たせる。MVPは tier 1 の6枚のみ
- **ステージ内は自由方式**：6枚は好きな順で進められる、ロックなし
- **ステージ間はしきい値ゲート**：ステージ内で3枚（半分）クリアしたら次のステージが開く（全クリアを待たない）
- MVP時点では tier 2 の中身はまだ無いので、3枚クリア達成時に「次のステージ（近日公開）」という**ロック解除演出だけ**を出す。README側で②③に既に使っている「ロック中プレースホルダー」の言語をそのまま流用し、実装コストを抑えつつ達成感を先に出す
- エントリー画面に6枚をシラバス的に並べ、各絵画に「未着手／完了」の状態を表示（既存のBentoGrid/Badgeのビジュアル言語を流用）
- セッション内（1枚をやっている最中）は「①気づきを書く → ②解説を読む → ③もう一度書く」の3ステップスタッパーを表示し、Round2必須であることを常に視認できるようにする
- ダッシュボードのBentoGridに「絵画ドリル: 3/6完了」等のカードを追加し、`NumberTicker`で既存デザインと統一感を持たせる
