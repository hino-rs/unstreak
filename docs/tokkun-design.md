# 特訓（弱点狙い撃ち再出題）設計ドキュメント

> このドキュメントは「弱点プール（プロダクトの心臓部）」の出題側——README で言及されているが未実装の部分——の設計をまとめたもの。実装はゆっくり進める前提で、優先順位付きのロードマップも兼ねる。

## 1. 背景・現状

README の「弱点プール」節にある通り、AI1 の添削結果と AI2 への質問ログを一元集約し、「自分が実際に詰まった構文・単語」だけを狙い撃ちで再出題するのが本来のコンセプト。

現状の実装状況：

- **書き込み側は実装済み**：`app/api/grade`（AI1添削）と `app/api/question`（AI2質問応答）の両方が `weak_points` テーブル（`concept_key` ごとの集計、`times_flagged` / `last_seen_at`）に反映している。`concept_key` は `lib/ai1.ts` の `toConceptKey` / `lib/ai2.ts` の `toConceptKeyFromLemma` で機械的に正規化（`grammar:articles`, `vocab:xxx` 等）。
- **読み出し側は「表示」のみ**：`app/(app)/review` と `app/(app)/dashboard` は `weak_points` を集計してグラフ・Bento Grid表示するだけで、アクションに繋がる導線がゼロ。
- **出題側は weak_points を一切見ていない**：`app/(app)/practice/describe/next-image/route.ts` はランダムに Unsplash 画像を選ぶだけで、弱点を反映した出題は行われていない。

→ つまり「記録」の入口はあるが、「狙い撃ち再出題」という出口が丸ごと欠けている。これを埋めるのが本ドキュメントの主題（「特訓」機能）。

## 2. concept_key の分類（v2: vocab / grammar でモード分割）

> **改訂**：当初はトークン型grammarをサクッとに、構築型grammarをしっかりに、という2軸分類だった（旧v1、末尾に記録）。サクッとのフォーマットB（穴埋め直行・完全一致採点）を文法に実装したところ、以下2つの問題が実運用で判明した。
>
> 1. **脈絡不足**：`drill_attempts.submitted_text` から誤り箇所だけを空欄化しても、元は「画像を見て書いた説明文」なので、写真を添えても文脈が伝わらないケースが頻発した。
> 2. **唯一の正解への固執**：冠詞・時制などの多くは、その場でAI1が選んだ1つの言い換えが「正解」として記録されるだけで、実際には文法的に妥当な選択肢が複数ありうる（"a dog" と "the dog" のどちらも成立しうる、等）。完全一致採点だと、正しい理解をしていても不正解（偽陰性）になる。
>
> 語彙でこの問題が起きなかったのは、`ai2_queries.question_text` がそもそも自己完結した手がかり文で、正解も単語・熟語単位でブレが少ないため。つまり問題の本質はフォーマット(A/B)の違いではなく、**vocabかgrammarかの違い**だった。
>
> → **結論**：サクッとは語彙専用に一本化（実装済み）。文法は全種別（トークン型・意味選択型・構築型を問わず）を、LLM（推論）で都度文脈十分な問題を生成し、意味的に採点する「しっかり」モードに統一する。

| 分類 | concept_key | 出題モード |
| --- | --- | --- |
| 語彙 | `vocab:*` | サクッと（フォーマットB、F素材、機械的採点、無料・実装済み） |
| 文法（全種別） | `articles`, `prepositions`, `past_tense`, `plural_agreement`, `subject_verb_agreement`, `present_perfect`, `modal_verbs`, `word_order`, `comparatives`, `conditionals`, `passive_voice`, `other` | しっかり（LLMによる問題生成＋意味的採点、要設計） |

以下、3〜6節はv1時点の設計内容（フォーマットA〜Fの定義、旧concept_key×フォーマット対応表）。しっかりモードの再設計時に参照しつつ書き換える。

## 3. 出題フォーマット一覧

| ID | 名称 | 概要 | 想起レベル | 採点方式 |
| --- | --- | --- | --- | --- |
| A | タップ→即インライン入力 | 文をそのまま表示し、怪しい箇所をタップ（検出）→その場で正しい形を入力（産出） | 手がかり想起 | 機械的（既知の空欄と一致判定） |
| B | 穴埋め直行 | 検出ステップを省き、最初から空欄を提示して打たせる | 手がかり想起 | 機械的 |
| C | 単語タイル並べ替え | 日本語キュー＋シャッフルされた英語チャンク（句単位）を並べさせる | 再構成（やや軽め） | 機械的（目標構造との突合） |
| D | 変形プロンプト | ベース文＋指示（「受動態にすると？」等）で自由記述させる | 自由想起 | LLM採点が必要 |
| E | 二文結合 | 関連する単文2つを目標構造でだけ結合させる（統制作文、CとDの中間） | 自由想起寄り | LLM採点が必要 |
| F | 素材調達方針（横断的） | 汎用文をAIに新規生成させるのではなく、本人の過去の誤答（`drill_attempts.ai1_response.errors` や `ai2_queries`）をそのまま再利用する | — | — |

F を使う場合、空欄位置・正解ともに DB 内のデータから機械的に構築できるため **LLM呼び出しが不要**。新規の例文が必要になった場合のみ AI 生成に頼る。

## 4. concept_key × フォーマット対応表

| concept_key | 主形式 | 補助形式 | 補足 |
| --- | --- | --- | --- |
| `articles` | B | A | 純トークン、冠詞探しの原体験そのもの |
| `prepositions` | B | A | 同上、closed-class |
| `past_tense` | B | A | 動詞活用のみ |
| `plural_agreement` | B | A | 名詞/数量詞の一致 |
| `subject_verb_agreement` | B | A | -s の有無 |
| `present_perfect` | B（形） | E（使い分け）, D | 形はトークンだが単純過去との使い分けは文脈依存。E で手がかり文＋主文を組ませて選択させる |
| `modal_verbs` | B（形） | D（場面）, A | should/must/can の選択は状況依存。D で場面設定文を出し選ばせる |
| `word_order` | C | E | 語順そのものが構築物、タイルが自然 |
| `comparatives` | E | C, D | 二文結合（価格等の事実→比較文）が最も構造を強制しやすい |
| `conditionals` | E | D | 二文結合が自然。C は節の前後入れ替えが両方正解になりうるため判定がやや面倒 |
| `passive_voice` | D | C, E | 能動→受動の変形が定番。語順が固定的なので C も成立する |
| `other` | D | - | 汎用フォールバック |
| `vocab:*` | B | A | フラッシュカード的。F との相性が最も良い |

同一 concept_key に複数フォーマットを割り当ててよい（優先度・気分・課金プランに応じて出し分ける）。

## 5. LLMコスト・課金境界

v2以降は、境界がそのままモード境界と一致する：

- **無料枠 = サクッと（語彙のみ）**：フォーマットB＋F素材（`ai2_queries`）。正解が既知・判定も機械的なので LLM 呼び出しゼロで成立する。実装済み。
- **有料枠寄り = しっかり（文法全般）**：問題生成・採点の両方にLLMが要る。既存の誤り（F素材、`drill_attempts.ai1_response.errors`）を種にしつつ、都度LLMに文脈十分な問題を組み立てさせ、意味的に採点する想定（要設計）。

## 6. UX・導線設計

### 6.1 ページの役割分担

- **振り返り（review）＝診断layer**：現状の Bento Grid 統計表示のまま維持。「見て内省する」モードなので、テンポの速い反復UIとは混ぜない。各カードに「この弱点を鍛える」的な小さいリンクを追加し、該当 concept_key を指定して特訓へ深リンクする。
- **特訓＝新規の主機能**：ナビの主要項目（ホーム/画像説明ドリル/日記/トピック説明/振り返り/設定と並ぶ階層）に追加する。理由：
  1. README 自身が弱点プールを「心臓部」と呼んでいる以上、そこへのアクセスが振り返りの奥に埋もれているのは扱いとして軽すぎる。
  2. 「予測成功率の推移」が本来の進捗指標である以上、その数値を動かす行為（＝反復すること）は毎日のホーム画面の主導線であるべき。
  3. 有料機能の訴求場所として、専用画面の方が導線設計がしやすい（統計を見に来た人の体験にペイウォールを混ぜたくない）。
- **ダッシュボード（ホーム）**：「今日の復習」CTA を主要導線として追加。旧来アプリのストリーク訴求の健全な代替として機能させる。

### 6.2 セッション強度の選択

語彙（数秒/問）と文法（LLM生成・LLM採点で数十秒〜分/問）を無差別に同一キューへ混ぜるとテンポが崩れる。特訓の入口でセッションの重さを選ばせる：

- **サクッと**（1〜2分、語彙のみ）＝ 無料枠（実装済み）
- **しっかり**（5分、文法全般）＝ 有料枠寄り、LLM問題生成＋意味的採点（要設計）

これは負荷選択であると同時に、そのまま課金境界としても機能する。

## 7. モチベーション設計原則

本アプリはストリーク/バッジを意図的に排除しているため（Goodhartの法則批判、README参照）、継続のための報酬機構を足す場合も同じ罠に陥らないよう設計原則を明文化しておく。

> **大原則**：報酬の対象は「行為の量」ではなく「実際の克服」に1:1で紐付ける。ログイン日数・問題数・XP のような量への報酬は導入しない。

具体案：

1. **卒業演出**：`weak_points` にマスタリー判定（連続正解カウント等）を追加し、閾値到達でプールから退場する瞬間を小さく祝う。行為の量では発生せず、実際に間違えなくなって初めて起きるためゲームできない。
2. **即時フィードバックの強化**：現状「予測成功率の推移」はダッシュボードで後から見る遅延集計のみ。特訓で正解した瞬間そのものに、もう少し満足感のあるマイクロインタラクションを足す。
3. **セッション終了サマリーの数え方**：「今日n問解いた」ではなく「今日n個の弱点に対処した（正解してマスタリー閾値に近づいた）」で見せる。前者は物量ゲームに堕ちやすいが、後者は質を伴わないと増えない。
4. **遅延した気まずさフックの活用**：README既存の「これ3週間前も聞いたよ」は、気づいた瞬間にすぐ直しに行ける導線（6.1の振り返り→特訓の深リンク）があって初めて効く。

## 8. データモデルへの示唆（未実装・要検討）

- `weak_points` に `consecutive_correct` 等のマスタリー用カラムが必要。現状 `times_flagged` は増える一方で減る経路がなく、克服した項目がプールに残り続ける。
- 特訓の出題履歴を記録するテーブル（仮 `tokkun_attempts`）が必要か検討：どの `concept_key` に対しどのフォーマットで出題し、正誤・所要時間を記録する。優先度スコア（`times_flagged` × 経過日数等）の計算にも使える。
- F素材の抽出元：文法系は `drill_attempts.ai1_response.errors`（`user_fragment` / `corrected_fragment` が既に保存されている）、語彙系は `ai2_queries`（`question_text` / `revealed_answer`）。
