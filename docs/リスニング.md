# リスニング機能 — アーキテクチャ仕様書

音声を「聞く」、テキストで「返す」を繰り返す、マイク不要のリスニング&アウトプット訓練機能。既存の英語学習SaaSへの組み込みを前提にまとめる。

## 1. 全体構成

3層構成。ブラウザはUI表示とTTS再生のみを担当し、会話生成（LLM呼び出し）は必ずバックエンド経由にする。

```
[ブラウザクライアント]  <──>  [あなたのバックエンド]  <──>  [Claude API]
   UI表示・TTS再生            会話履歴管理・API中継           会話文生成
```

**重要**: プロトタイプ（Claude.aiのArtifacts上のデモ）では `fetch("https://api.anthropic.com/v1/messages")` をブラウザから直接叩いていましたが、これはArtifacts環境専用のサンドボックス機能で、APIキーなしで動く特殊な仕組みです。実際のSaaSでは **必ずサーバーサイドでAPIキーを保持し、クライアントからは自前のバックエンドAPIを叩く** 構成にしてください。クライアントに`ANTHROPIC_API_KEY`を露出させると即座に悪用されます。

## 2. コンポーネント詳細

### 2-1. フロントエンド（ブラウザ）
- 会話UI（吹き出し表示、入力欄、再生速度・ミュート設定）
- TTS再生: 実装方式は2択（3章で比較）
- 状態管理: 会話ログ、ローディング状態、再生状態のみ。会話の「正」データはバックエンドのDBに置き、フロントは表示用キャッシュとして持つ

### 2-2. バックエンド
- 会話エンドポイント: ユーザーの発言を受け取り、Claude APIを呼び出し、応答を返す
- 会話履歴（セッション）の永続化
- システムプロンプトの組み立て（トピック・レベル設定を反映）
- レート制限・利用量管理（ユーザーごとのAPI利用コスト管理に直結する）

### 2-3. Claude API連携
- モデルは [Anthropic公式ドキュメント](https://docs.claude.com) で現行の推奨モデルを確認して選定（学習会話のような短い応答中心の用途ならコストと速度のバランスが良いモデルが向く）
- `system` パラメータに以下を含める:
  - レベル別の語彙・文長の指示
  - トピック（雑談/旅行/ビジネス等）
  - 「学習者はTTSで聞いてテキストで返信する」という前提
  - 文法を明示的に訂正しない、自然な会話を優先、といった振る舞いの指示
- 長い会話が続くとコンテキストが肥大化するため、一定ターン数を超えたら古い履歴を要約して圧縮する設計を推奨
- 体感速度を上げたい場合はストリーミングレスポンス（SSE）に対応し、生成中のテキストを逐次表示

## 3. TTS方式の比較

| 方式 | メリット | デメリット |
|---|---|---|
| ブラウザ標準TTS（Web Speech API / `SpeechSynthesis`） | 無料、追加インフラ不要、実装が簡単 | 端末・ブラウザで音質や声が変わる（特にAndroid/Windowsで機械的になりやすい）。iOS Safariはユーザー操作なしでの自動再生に制限あり |
| クラウドTTS API（Amazon Polly、Google Cloud TTS、ElevenLabs等） | 声質が安定・高品質、SSMLで間や強弱を制御可能、音声ファイルをキャッシュしてCDN配信できる | 文字数課金でコストが発生、レイテンシがブラウザTTSより増える、バックエンド実装が必要 |

学習系SaaSとしての体験を重視するなら、無料プランはブラウザTTS、有料プランはクラウドTTS（高品質ボイス選択可）という段階分けが現実的な落としどころ。

## 4. データモデル例

```
conversations
  id, user_id, topic, level, created_at

messages
  id, conversation_id, role (user | assistant), content, created_at

user_settings
  user_id, default_level, default_speed, voice_preference
```

## 5. APIエンドポイント例

```
POST /api/conversations
  body: { topic, level }
  → 新規会話を作成し、AIの最初の発話を返す

POST /api/conversations/:id/messages
  body: { content }
  → ユーザーの発言を保存し、Claude APIを呼び出して応答を保存・返却

GET /api/conversations/:id
  → 会話履歴の取得（画面リロード対応）
```

## 6. 実装上の注意点

- **APIキーの管理**: サーバー環境変数のみに保持。クライアントには絶対に渡さない
- **iOS Safariの自動再生制限**: 初回の音声再生はユーザーのタップ等の操作をトリガーにする必要がある（「はじめる」ボタン押下時に一度無音再生してAudioContextをアンロックする、等の対応が定番）
- **コスト管理**: `max_tokens`の上限設定、会話ターン数の上限、無料/有料プランでのモデル・利用回数の出し分け
- **音声認識(STT)は不要**: この機能はユーザー発話を聞き取る必要がなく、テキスト入力のみのため、マイク権限やSTTの実装コストがかからず比較的シンプルに組み込める
- **学習ログとしての拡張性**: メッセージテーブルをそのまま学習履歴・語彙頻度分析・進捗トラッキングに転用しやすい設計にしておくと後の機能追加が楽になる

## 7. 使用技術まとめ

| レイヤー | 技術 |
|---|---|
| フロントエンド | 任意のSPAフレームワーク（React/Vue等）+ Web Speech API または クラウドTTS SDK |
| バックエンド | 任意の言語/フレームワーク + Anthropic公式SDK（TypeScript/Python） |
| LLM | Claude API（`/v1/messages`、`system`パラメータで人格・レベル・トピックを制御） |
| DB | 会話・メッセージ・ユーザー設定を保存できるRDB（PostgreSQL等）で十分 |
| （任意）TTS | Amazon Polly / Google Cloud TTS / ElevenLabs 等 |

## 8. 拡張アイデア

- 会話終了後に間違いやすかった表現をやんわりフィードバック
- 頻出単語をピックアップして復習リストに追加
- レベルを会話の出来に応じて自動調整（アダプティブ難易度）
- 再生速度・語彙難易度のA/Bテストで学習効果を計測
