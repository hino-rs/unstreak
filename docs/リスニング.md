# リスニング機能 — 設計ドキュメント

> 音声を「聞く」、テキストで「返す」を繰り返す、マイク不要のリスニング&アウトプット訓練機能。

## 0. 改訂の経緯

初版は「音声(AI)⇄テキスト(USER)という構成の英会話は市場に少ない」という着眼から、技術アーキテクチャのみをまとめたものだった。しかしその後の検討で、以下の2点が見えた。

1. Unstreak既存の差別化要素（弱点プールへの集約、生成効果を使ったUX摩擦設計、Goodhartの法則への警戒）が組み込まれておらず、このままでは既存の「音声⇄音声/テキスト⇄テキスト」勢と同じ土俵の汎用会話ボットになってしまう
2. 目標設定が曖昧だった。「英語圏の海外で、聞き取れないことがほとんどないレベル」という具体的な到達点と、「聞き返すのも実力のうち」という方針を軸に据えると、設計の焦点が大きく変わる

本ドキュメントはこの2点を反映した改訂版。初版の技術的な注意点（APIキー管理、iOS Safari制約など）は引き継ぐ。

## 1. 到達目標の定義

「聞き取れないことがほとんどない」を測定可能な形に分解する。実際に聞き取りを妨げる要因は語彙量そのものより、以下の軸にほぼ集約される。

| 軸 | 内容 | 低難度 | 高難度 |
| --- | --- | --- | --- |
| 話速 | Rate | ゆっくり・明瞭 | ネイティブ会話速度・早口 |
| アクセント | Accent | 標準的な米語 | 英/豪/印などの非標準アクセント、訛りの強い話者 |
| 連結・脱落 | Connected speech | citation form寄り | gonna/wanna/didja等、日常会話の自然な省略・弱形が高密度 |
| 環境音 | Noise | 無音 | カフェ・空港・電話越しの音質劣化・BGM等 |
| 話題の予測可能性 | Topicality | 定型シナリオ（自己紹介・注文） | 脱線混じりの雑談、専門的な小話 |
| 対話性 | Interactivity | 対話（聞き返し可能） | 一方向（駅・空港アナウンス等、聞き返し不可） |

「聞き取れないことがほとんどない」＝これら全軸が最高難度でも、対話（モード1）なら聞き返しで会話を破綻させずに続けられる、一方向（モード2）なら要点（時刻・場所・番号等）を落とさず拾える、と操作的に定義する。ユーザー体験としては軸を個別スライダーで見せず、後述のTierにまとめて提示する（絵画ドリルの`tier`概念を踏襲）。

## 2. コアコンセプト：聞き返しは失敗ではなく訓練対象のスキル

前回の検討では「聞き返しボタン→弱点シグナルとして記録」という設計を考えていたが、方針が変わったことで設計の軸が変わる。

- 海外生活で実際に効くのは「一度で全部聞き取れる耳」より「聞き取れなかった時に自然に切り返して会話を止めずに済ませる力」。これは現地日常でほぼ毎日発生する
- したがって聞き返しを「ワンクリックで書き起こしが出るショートカット」にはしない。**聞き返しの一言自体を英語で産出させ、それに対してAIが自然な相手として応答する**（繰り返す/言い換える/ゆっくり言い直す）。これはUnstreakの産出仮説と直接一致する（聞き取れない場面でこそ、とっさの英作文力が試される）
- 書き起こし表示（完全な答え合わせ）は最終手段として残すが、聞き返しを2回試みても埒が明かない場合にのみ開放する。絵画ドリルのReveal（Round1を経ないと出さない）と同じ思想
- 聞き返しの文章自体（"Sorry, come again?" のバリエーション・自然さ・タイミング）も添削・記録の対象にする。「毎回"What?"としか言えない」状態も一種の弱点として扱う

## 3. コアループ

**モード1（対話）**
```
AI発話(音声) → ユーザーは
  (a) 会話として返信する
  (b) 聞き取れなかった一言を英語で入力する（"Could you say that again?" 等）
       → AIが自然な相手として繰り返す/言い換える/ゆっくり言い直す
       → 再度(a)(b)を選べる。2回目の聞き返しでも詰まったら「書き起こしを見る」を開放
→ 会話継続。数ターンごとに自然な形で内容理解を要する応答を挟む（強制クイズ化しない）
```

**モード2（一方向・アナウンス系）**
```
AI発話(音声、聞き返し不可) → ユーザーは聞き取れた要点（時刻・場所・番号・注意事項等）を
  テキストで書き出す → 提示された正解要点と突き合わせて自己採点
```
モード2は聞き返せない実世界の場面（構内放送・機内アナウンス・電話の留守電等）を再現する。対話中心のモード1だけでは「聞き返せば何とかなる」設計に寄りすぎるため、両輪で持たせる。

## 4. シナリオ設計（コンテンツモデル）

絵画ドリルのfact-baseパターンを踏襲し、完全自由生成ではなく事前設計されたシナリオメタデータをベースにLLMが会話を生成する。難易度・仕込む聞き取り障害を制御するため。

| シナリオ例 | モード | 想定される聞き取り障害 |
| --- | --- | --- |
| 空港の保安検査 | 対話 | 早口・定型指示の省略（"gotta take that out"） |
| カフェでの注文 | 対話 | "What can I get started for ya?" 等の脱落 |
| 道を尋ねられる | 対話 | 訛り（豪・英） |
| 職場の雑談 | 対話 | イディオム多用（"I'm swamped" "let's circle back"） |
| 電話でのアポ変更 | 対話 | 音質劣化＋早口 |
| 駅・空港のアナウンス | 一方向 | 反響・BGM・早口の定型放送文 |

シナリオごとに以下を持たせる：
```
situation_brief      場面設定（ユーザーには開始前に一言だけ提示）
target_vocab          このシナリオで意図的に使う語彙
target_reductions     意図的に混ぜる連結・省略パターン（gonna/wanna等）
tier                  難易度段階（後述）
mode                  dialogue | monologue
voice_accent          使用するTTS音声（アクセント）
base_rate             基準話速
noise_profile         重ねる環境音（なし/カフェ/空港/電話）
```

## 5. 難易度・アダプティブレベル管理

第1章の6軸を個別スライダーとしてユーザーに見せるのは複雑すぎるため、MVPでは**Tier（1〜5程度）にバンドルして提示**する。Tierごとに6軸の目安値をセットで持つ（絵画ドリルの`tier`概念と同じ発想）。

- Tierの昇降は既存の`level_score`（AI1由来、産出面の実力指標）とは別軸で持つ。リスニングは受容側のボトルネック（音の分解能・アクセント慣れ）が主で、産出速度とは相関はあるが別物
- 更新シグナル：
  - 聞き返し発生率（低いほど聞き取れている）
  - モード2の要点正答率
  - 会話の噛み合い度（暗黙シグナル、後述、緩やかな重み）
- 既存`level_score`と同じくEWMAで更新し、1件の外れ値で急変しないようにする。αは小さめ（0.15〜0.2目安）
- 絵画ドリルの「気づき判定を厳密一致にしたら不利になった」という反省を踏まえ、噛み合い度判定は**厳密なYes/Noにせず、弱いシグナルとして重みを小さくする**。誤検知でTierが不当に下がらないようにする

## 6. 弱点プール統合

シグナル源を2種類に分ける。

1. **明示シグナル**：聞き返しが発生した瞬間、対象フレーズ・省略パターンを`toConceptKey`経由で弱点プールに投入する。既存AI2の質問ログと全く同じ形で、テキスト非依存のため無改造で流用できる
2. **暗黙シグナル**：ユーザーの返信がAIの発話と噛み合っていない場合（的外れな返答）に、聞き取れていなかった可能性として緩く記録する。自己申告に頼らない「誤魔化しの効かない実力指標」というREADMEの思想と一致するが、判定を厳しくしすぎると産出力不足（聞き取れてはいるが返し方が下手なだけ）と混同するリスクが大きい。**MVPでは明示シグナルのみを実装し、暗黙シグナルは後回しにする**のが妥当

弱点プールに投入する概念キーは、単語単位だけでなく「連結・省略パターン」（例：`gonna`, `wanna`, `didja`）単位でも持たせる。これにより、聞き取れなかった原因が「単語を知らない」のか「知っている単語の省略形が聞き取れない」のかを弱点プール上で区別できる。既存の画像ドリル・絵画ドリルにはない、リスニング特有の弱点カテゴリになる。

## 7. AIの役割分担（README追記案）

- **AI4（会話・音声相手役、新設）**：シナリオに基づき音声で発話し、ユーザーの返信・聞き返しに自然な相手として応答する。文法を明示的に訂正せず、自然な会話を優先する（初版の方針を継承）
- **AI1（既存・添削役）の再利用**：セッション終了後、ユーザーの聞き返し文・返信文をまとめて添削し、弱点プールに反映する。新規AIを増やさず、テキストを見て添削する既存タスクとして流用する
- AI2（辞書相棒）は従来通り、シナリオと無関係にいつでも呼び出せる導線として維持する

役割を増やしすぎない方針（AI4のみ新設）は、絵画ドリルでAI3を新設した際の「事実の捏造リスクをAI3の役割分離で断つ」という判断とは異なり、リスニングでは事実の正しさが論点ではなく会話の自然さが論点のため、既存AI1の再利用で足りると判断した。

## 8. TTS・音声設計

初版では「無料プランはブラウザTTS、有料はクラウドTTS」という単純な2択にしていたが、目標水準（アクセント・自然な省略・雑音耐性）を満たすには不十分。

| 要件 | 対応方針 |
| --- | --- |
| アクセントの多様性 | ブラウザ標準TTS（Web Speech API）は端末依存でアクセント制御が事実上できない。クラウドTTS（Amazon Polly Neural、Google Cloud TTS、ElevenLabs等）で複数アクセントのボイスを用意する必要があり、この機能は実質クラウドTTS前提になる |
| 話速制御 | SSMLの`rate`、またはTTS APIのspeed設定で制御。Tierごとに基準値を持つ |
| 連結・省略の自然さ | 高品質ニューラルTTSはconversational/casualなスタイル指定と自然な会話文（"gonna" "wanna"等を含む台本）を与えれば、綴りに引っ張られず自然な弱形で発話される。台本自体（LLM生成テキスト）にカジュアルな崩し表記を混ぜることが重要で、TTS側の設定だけでは不十分 |
| 環境音・電話品質 | サーバー側で音声合成時にミックスするのではなく、**クライアント側でWeb Audio APIを使い、TTS再生に背景音ループ（カフェ/空港等）を重ねる、または電話品質再現用にBiquadFilterNodeでバンドパスをかける**方式が軽量。追加のTTS課金・レイテンシが発生しない |

初版のiOS Safari自動再生制限・APIキー管理・コスト管理（`max_tokens`上限、ターン数上限）に関する注意点はそのまま有効。

## 9. UI/UXフロー・摩擦設計

- 聞き返し入力欄は会話入力欄と兼用にせず、「聞き取れなかった？」という軽いトグルで切り替える。心理的コストをゼロに保つため、聞き返しを選ぶこと自体への抵抗感は出さない（README冒頭のUX摩擦設計の1軸目と一致）
- 聞き返しの書き方が全く分からないユーザー向けに、画像ドリルの「書き出しヒント」と同じ発想で、折りたたみ式の定型フレーズ例を2〜3個だけ用意する（白紙で固まる問題を回避しつつ、コピペで終わらせず自分で打たせる）
- 書き起こし表示（最終手段）は聞き返し2回失敗後にのみボタンが現れる。使用したこと自体もログに残し、振り返り画面で低頻度なら肯定的に、高頻度なら「聞き返しで粘れる場面が増えてきたね」等、恥ではなく成長の言い回しで見せる
- 恥・気まずさの演出は初版の方針通り、質問・聞き返しの瞬間には出さず、振り返り画面でのみ「このパターン（gonna）、先週も聞き返してるよ」のように遅延して出す

## 10. データモデル

```
listening_scenarios
  id, title, mode (dialogue | monologue), tier,
  situation_brief, target_vocab (json), target_reductions (json),
  voice_accent, base_rate, noise_profile

listening_sessions
  id, user_id, scenario_id, tier_at_start, created_at, completed_at

listening_turns
  id, session_id, role (ai | user),
  turn_type (utterance | user_reply | clarification_request | ai_clarification_response),
  content, audio_params (accent/rate/noiseのスナップショット), created_at

clarification_events
  id, session_id, turn_id, target_phrase, concept_key,
  resolved (bool), transcript_revealed (bool), created_at

listening_profile
  user_id, tier_score (EWMA), clarification_rate (EWMA), last_updated
```

## 11. APIエンドポイント例

```
POST /api/listening/sessions
  body: { scenario_id }
  → 新規セッションを作成し、AIの最初の発話（音声込み）を返す

POST /api/listening/sessions/:id/turns
  body: { type: "reply" | "clarification", content }
  → type=reply: 会話を継続し、裏で噛み合い度を緩く判定（暗黙シグナル、後回し実装可）
  → type=clarification: AIは繰り返し/言い換えで応答し、明示シグナルをclarification_eventsに記録

POST /api/listening/sessions/:id/reveal-transcript
  → 最終手段の書き起こし表示（聞き返し2回失敗後などの条件下でのみ許可）。使用有無をログに残す

GET /api/listening/sessions/:id/summary
  → セッション後フィードバック（AI1による聞き返し文・返信文の添削、弱点まとめ）
```

## 12. 実装上の注意点（初版から継承）

- **APIキーの管理**：サーバー環境変数のみに保持。クライアントには絶対に渡さない
- **iOS Safariの自動再生制限**：初回の音声再生はユーザー操作をトリガーにする（「はじめる」ボタン押下時に無音再生でAudioContextをアンロック等）
- **コスト管理**：`max_tokens`の上限、会話ターン数の上限、無料/有料プランでのモデル・利用回数の出し分け。クラウドTTS前提になったことで、TTSの文字数課金もコスト管理対象に加える
- **音声認識(STT)は不要**：聞き返しも含め入力は常にテキストのため、マイク権限・STT実装は不要のまま
- **学習ログとしての拡張性**：`listening_turns`・`clarification_events`は語彙頻度分析・進捗トラッキングに転用しやすい設計にしておく

## 13. ロードマップ（MVP切り分け）

| フェーズ | 内容 |
| --- | --- |
| MVP | モード1（対話）のみ、Tierは2〜3段階、アクセントは米語標準のみ、環境音なし、明示シグナルのみ弱点プールに投入 |
| 拡張1 | モード2（一方向アナウンス）追加、環境音（クライアント側Web Audio）追加 |
| 拡張2 | アクセントバリエーション追加、暗黙シグナル（噛み合い判定）追加、Tier軸を6軸に分離した内部制御へ移行 |
| 拡張3 | 実録音声（ポッドキャスト・映画クリップ等）の導入検討。ライセンス・コンテンツ管理コストが増えるため優先度は低い |

## 14. 未解決の論点

- **優先順位**：README上のMVPは①画像描写ドリルのみで、②③はロック中のプレースホルダー段階。リスニングはロードマップに存在しない新規機能追加であり、②③より先に着手する理由（差別化の強さ、実装コスト、ユーザーの痛みの強さ）を別途整理する必要がある
- **需要検証**：「聞き取れないことがほとんどないレベル」を目指すユーザーが、既存ユーザー層（README冒頭のDuolingo疲れ層）にどれだけ重なるかは未検証。オンボーディング時のヒアリングやMVP後の利用ログで確認する
- **暗黙シグナルの精度**：会話の噛み合い判定をどこまで信頼してTier調整に使うかは、実データを見てから閾値を決める必要がある
