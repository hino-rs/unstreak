- **課金基盤の実装は完成している。** RLS分離・`SECURITY DEFINER` RPC・Webhook冪等性・返金経路・実機検証まで到達済み。「作れるか」は既に証明された

## P0: 本番課金を開始する前に必ず終わらせる

- [x] AI呼び出しにプロンプトキャッシングを導入する（2026-09-05 完了）
- 入力トークンが原価の支配項であり、キャッシュ読み出しは約1/10のコストになる。仕様変更を伴わない純粋な利益であり、他のどのコスト対策よりリスクが低い
- **導入したのは `lib/ai1.ts`（2箇所）と `lib/ai5.ts` の計3箇所。** ai1は system を「固定ルール（breakpoint付き）」と「levelInstruction＋detailedInstruction」の2ブロックに分割した。可変部を同じブロックに残すとレベル3種×detailed2種＝6通りのprefixに分裂しヒット率が1/6になるため。`tools → system → messages` の順にレンダリングされるので、system先頭ブロックのbreakpointはツールスキーマごとキャッシュする。ai5は system と「直近ターンの末尾」の2箇所にbreakpointを置き、毎ターン再送される履歴を増分キャッシュする
- **`lib/ai2.ts` `ai3.ts` `ai4.ts` には入れていない（当初計画からの変更）。** 3つとも Haiku 4.5 で、このモデルだけキャッシュ最小prefixが4,096トークンと突出して高い（Opus 5は512、Sonnet 5は1,024）。実測は ai2 の system が約660、ai3 が約780、ai4 は tools+system で約1,280トークンといずれも遠く届かない。**`cache_control` を付けてもエラーにならず黙って無効化されるだけ**なので、あえて付けずに理由をコード側にコメントとして残した。「リスニングにprefixキャッシュが最も効く」という当初の見立ては誤り
- **実測（実APIで検証済み）**: ai5/Opus 5 の3ターン会話で `cache_read_input_tokens` = 0 → 1,204 → 1,515、非キャッシュ入力は23トークンまで低下。ai5/Sonnet 5（無料・Standard）も2ターン目で1,272読み出し。ai1.gradeDescription は2回目で1,666、gradeTopicSession は1,971を読み出し。**ターンあたりの削減はai5で約50〜63%**（入力側のみ。出力トークンは変わらない）
- **`lib/anthropic.ts` に `logAiUsage()` を追加した。** `usage` を読む経路がコードベースに存在せずキャッシュの検証自体ができなかったため。`{"tag":"ai_usage",...}` の構造化ログを1行出すだけの最小実装で、Sentry / アナリティクス導入までの繋ぎ。全5箇所のAI呼び出しに設置済み（打ち切り時も原価は出るので `stop_reason` のthrowより前に置いてある）
- **副産物**: ai5/Opus 5 の出力トークンは実測で1ターン92〜107にとどまった。adaptive thinking がこの単純なタスクではほとんど思考していないため、下の「`output_config.effort` を指定するか」の判断は**コスト面ではほぼ無価値**（削減余地は1ターン数十トークン）。品質面だけで決めてよい

- [x] AI1のモデルを `claude-sonnet-4-6` から `claude-sonnet-5` に移行する（2026-09-04 完了）

## P1: 収益が積み上がるために必要

- [ ] アナリティクスを導入する
- PostHog または GA4。最低限、LP到達 → 登録 → 初回ドリル提出 → 2回目提出 → 課金 のファネルと、プラン別の継続率を取る
- 現状すべての改善判断がカンになる。特に「無料→有料の転換率」と「churn率」は、到達可能な規模の逆算に直接使う変数であり、これが無いままP2の価格改定を判断することはできない。**以降のタスクの効果測定が全部これに依存する**

- [ ] 弱点マップの蓄積を無料層にも可視化する
- 現在この蓄積が見えるのは `/review` のPro限定トレンドセクションのみ。無料・Standardにも「これまでに記録された弱点の総数」「最も繰り返している構文」「記録期間」といった厚みを見せる。数値の推移そのものはPro限定のままでよい
- ストリークを思想として捨てた以上、代替の継続エンジンが要る。3ヶ月分の自分専用の弱点マップは他アプリに持ち出せない、正真正銘のスイッチングコスト。これが唯一ストリークの代わりになる資産で、しかも実力と連動しているのでプロダクト思想と矛盾しない。**サブスクのLTVを決めるのはこの一点**

- [ ] オンボーディングを作る
- 登録直後に、プロフィール（職業・趣味＝トピック説明の前提条件）の入力と、画像描写ドリル1回の完了までを一本道で案内する
- トピック説明はプロフィール未設定だと `400 profile not configured` で使えない。最も差別化になる機能に、初回ユーザーが偶然たどり着かないと使えない構造になっている。初回体験の完了率は転換率に最も強く効く

- [ ] クレジット残高の事前表示と事前ブロックを実装する
- 各消費画面で残高と今回の消費量を提出前に表示し、不足時はボタンを無効化して購入導線を出す。現状は402エラーハンドリングのみ
- 長文を書いた直後に402が出るのは、課金導線として最悪のタイミング。ユーザーは「買おう」ではなく「損した」と感じる。トップアップは月中のクレジット切れの受け皿として設計されているのに、その受け皿に誘導する導線が無い

- [ ] 402/429を画面ごとに個別メッセージで案内する
- `app/(app)/practice/describe/page.tsx:192-193` は `response.ok` がfalseなら常に「採点中にエラーが発生しました」を返す。絵画ドリル側は402→クレジット不足、429→時間をおいて、と出し分けており不揃い
- 「クレジット不足」を「エラー」と表示することは、購入機会を障害として見せることに等しい。上の事前ブロックが入るまでの間、これが最後の防波堤になる

- [ ] ダッシュボードのダミーデータ表示をやめる
- `app/(app)/dashboard/dashboard-view.tsx:211-256` の `fallbackDrills` は、提出履歴が0件のとき実データと見分けのつかない見た目でハードコードされたサンプルを表示する。空状態のUIに置き換える
- 初回ユーザーが最初に見る画面で、身に覚えのない添削結果が並ぶ。プロダクトの信頼性そのものを損なう上に、「何をすればいいか」を伝える空状態の機会を潰している

- [ ] LPのSEO・OGP対応
- `app/(marketing)/page.tsx` にメタデータ、OGP画像、構造化データ。「英語 話せない アプリ」「ストリーク 意味ない」といった原体験に近い検索意図を狙う
- 月330人の新規登録を安定供給するには、バズ頼みではなく細くても継続する流入が要る。LPの本文は既に強い（原体験ベースの共感セクション）ので、見つけられるようにするだけで効く

- [ ] カスタマーサポート導線を用意する
- 問い合わせ先（メールまたはフォーム）を設置し、特商法ページ・利用規約からリンクする
- 特商法上の連絡先開示義務に加え、決済トラブルの申告経路が無いとユーザーの次の行動がカード会社へのチャージバックになる。Stripeアカウントの健全性に直接響く

- [ ] サブスク解約・返金時のクレジット扱いを明文化する
- 解約時に残ったクレジットをどうするか、プラン変更時の残高をどう扱うかを利用規約に定め、実装と一致させる
- 上のクレジット有効期限と合わせて、ここが曖昧なままだと個別対応の判断がその都度必要になる。有料ユーザーが増えてから決めると、既に払った人への遡及適用の問題が発生する

## 対象外と判断したもの

- **TOTP MFA**: 決済情報はStripe側にあり本サービスは保持していない。Turnstileまでで当面は釣り合う
- **音声入力・発音評価**: READMEの理論的裏付け（Leveltの発話生成モデル）が、音声を使わずテキストで鍛えても話す力に転移するという立場を取っている。ここに手を出すとELSA/Speakとの真っ向勝負になり、原価も跳ね上がる。差別化を捨てる方向の投資
- **月商100万円規模を前提とした施策**: 新規無料登録3,300人/月を継続的に必要とし、現状のチャネル構成では非現実的。10万〜30万を目標に設計する
