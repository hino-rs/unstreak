# クレジット・決済導入 記録

> 2026-08-14〜15 にかけて実装したクレジット制と Stripe 決済連携の記録。実装規模が大きく開発者自身もコード全体を追い切れていないため、後から仕様・意図・既知の課題を追えるように残す。

## 1. 背景・目的

unstreak は Claude 呼び出し（画像描写採点、AI2質問応答）と Unsplash 画像取得を無制限に許可しており、Upstash Redis によるレート制限のみで乱用を防いでいた。これに「クレジット」の概念を導入し、以下をトリガーに付与・消費する仕組みを追加した。

- **付与トリガー**: サインアップ時ボーナス／Stripeサブスク登録（月次）／Stripeクレジット都度購入
- **消費トリガー**: AI呼び出し・画像取得を伴う機能

金額・クレジット数は本記録時点で未確定のため、コードにハードコードせず env var で調整可能にしている。

## 2. なぜ専用テーブルに分離したか

既存の `profiles` テーブルの `update own profile` ポリシーは `using (auth.uid() = user_id)` のみで **`with check` もカラム制限もない**。もし `credits` カラムを `profiles` に足すと、ログイン済みユーザーがクライアントSDKから直接自分のクレジットを書き換えられてしまう。

そのため `credit_balances` / `credit_transactions` を新設し、**書き込みは全て `SECURITY DEFINER` のRPC経由**（もしくはStripe Webhookのservice-roleクライアント）に限定した。`authenticated`ロールに対するテーブル直接のINSERT/UPDATEポリシーは意図的に一切作っていない。

## 3. スキーマ

`supabase/migrations/20260814120000_add_credit_system.sql`

| テーブル | 役割 | RLS |
| --- | --- | --- |
| `app_config` | 運用パラメータ（`signup_bonus_credits`など）。再デプロイなしでSQL UPDATEのみで変更可能 | ポリシーなし＝`authenticated`/`anon`から完全に不可視。`SECURITY DEFINER`関数からのみ読める |
| `credit_balances` | 残高（`credits`, `CHECK (credits >= 0)`）＋Stripe連携情報（`stripe_customer_id` UNIQUE, `stripe_subscription_status`）。1ユーザー1行 | `select own`のみ。書き込みポリシーなし |
| `credit_transactions` | 元帳。監査・冪等性の唯一の情報源。`delta`, `reason`, `stripe_event_id`（UNIQUE, nullable） | `select own`のみ。書き込みポリシーなし |

`stripe_event_id`はnullable + UNIQUE。NULL同士は衝突しない（signup_bonus等の非Stripe理由に必要）が、Stripeイベントは一度しか適用されない（Webhook再送耐性＝冪等性の仕組み）。

## 4. RPC関数

同マイグレーション内。全て`security definer set search_path = public`。

| 関数 | 呼び出し元 | 認可 | 役割 |
| --- | --- | --- | --- |
| `consume_credit(p_user_id, p_amount, p_reason)` | `authenticated`（アプリのAPIルート） | 内部で`auth.uid() = p_user_id`を検証 | 原子的な条件付き減算＋元帳挿入。残高不足なら`false`を返す |
| `refund_credit(p_user_id, p_amount, p_reason)` | 同上 | 同上 | `consume_credit`の逆操作。AI呼び出し失敗時の自己返金専用 |
| `grant_credit(p_user_id, p_amount, p_reason, p_stripe_event_id)` | **`service_role`のみ**（Webhook／`handle_new_user`トリガー内部） | **`auth.uid()`チェックを持たない**。EXECUTE権限を`service_role`のみに絞ることが唯一の防御線 | `stripe_event_id`の`ON CONFLICT DO NOTHING`で冪等に付与 |
| `set_stripe_customer_id(p_user_id, p_stripe_customer_id)` | `authenticated`（checkoutルート） | `auth.uid()`チェック | admin clientをwebhook以外に持ち込まないための最小RPC |

`handle_new_user`トリガーを更新し、`profiles`作成に加えて`app_config.signup_bonus_credits`を読んで`grant_credit`をPERFORMするようにした。

## 5. クレジット消費ポイント

`lib/credits.ts`の`CREDIT_COSTS`（各値は`CREDIT_COST_*` env varで上書き可）。

| 機能 | ルート | コスト | 返金/課金タイミング |
| --- | --- | --- | --- |
| 画像描写採点（Claude Sonnet） | `app/api/grade/route.ts` | 3 | `withConcurrencyLock`内で消費→AI呼び出し失敗時は`refundCredit`して再throw |
| AI2質問応答（Claude Haiku） | `app/api/question/route.ts` | 1 | 同上 |
| 次の画像取得（Unsplash） | `app/(app)/practice/describe/next-image/route.ts` | 1 | **未見の画像が確定した直後**、レスポンス直前のみ消費。5回リトライしても見つからない409（在庫切れ）パスは課金しない |
| クイック特訓（DB完結、AI呼び出しなし） | `app/api/training/quick/*` | 0 | 変更なし |

`InsufficientCreditsError`が投げられた場合、各ルートはHTTP **402**を返す。

## 6. Stripe連携

- `lib/stripe.ts`: `new Stripe(process.env.STRIPE_SECRET_KEY!)`
- `app/api/stripe/checkout/route.ts`: `{ mode: "subscription" | "topup" }`を受け取りCheckout Sessionを作成。`credit_balances.stripe_customer_id`が無ければStripe Customerを作成し`set_stripe_customer_id`で保存
- `app/api/stripe/portal/route.ts`: `stripe_customer_id`からBilling Portal Sessionを作成
- `app/api/stripe/webhook/route.ts`: 生ボディ＋署名検証（`STRIPE_WEBHOOK_SECRET`）。ハンドリングするイベント:
  - `checkout.session.completed`（`mode === "payment"`＝都度購入のみ。サブスクの初回分はここで付与しない＝`invoice.paid`と二重付与になるため） → `grant_credit`（理由`stripe_topup`）
  - `invoice.paid` → サブスクの`metadata.supabase_user_id`と価格から`grant_credit`（理由`stripe_subscription`）
  - `customer.subscription.created` / `.updated` / `.deleted` → `credit_balances.stripe_subscription_status`を直接UPDATE
- `proxy.ts`のmatcherから`api/stripe/webhook`を除外（セッションミドルウェアをバイパスさせる衛生上の措置）
- `PRICE_CREDIT_GRANTS`（`lib/credits.ts`）でStripe Price ID → 付与クレジット数を対応付け（env var経由）

## 7. Tier1: 認証まわりのレート制限強化

Stripe決済導入にあたり、Stripe Japanの「セキュリティ対策措置状況申告書」（クレジット取引セキュリティ対策協議会のチェックリスト）に対応するため、`app/(auth)/actions.ts`の`login`/`signup`にIPアドレス＋メールアドレスベースのブルートフォース対策を追加（`lib/rate-limit.ts`）。

- IPベース: 10回/60秒（`x-vercel-forwarded-for` > `x-forwarded-for` > `x-real-ip`の優先順、IP不明時はスキップ）
- メールベース: 5回/300秒（IPを跨いだ同一アカウントへの集中攻撃対策）

申告書の「ログイン試行回数の制限とスロットリング」に対応する実装。Supabase Dashboard側の`Confirm email`（登録通知）・`Rate Limits`（デフォルトのIP制限）も合わせて確認済み。MFA・CAPTCHA・IP評判ベースの制限・行動分析・デバイスフィンガープリントは未実装（Tier2/3として見送り）。

## 8. 実装後に発見・修正したバグ

いずれも実装直後のセルフレビュー・実機テスト・`/code-review`スキルでの検証で発見。

1. **Stripe SDK v22の破壊的変更**: `Invoice.subscription`が廃止され`invoice.parent.subscription_details.subscription`に移動していた。`webhook/route.ts`の`invoice.paid`ハンドラで修正済み。
2. **`customer.subscription.created`未処理**: サブスク新規作成時に最初に発火するのは`.created`だが、`.updated`/`.deleted`しか処理していなかったため`stripe_subscription_status`がNULLのまま＝Billing Portalへの導線（「管理」ボタン）が出ない不具合。`.created`もハンドリング対象に追加して解消（`webhook/route.ts`）。
3. **`set_stripe_customer_id`が握りつぶされる**: このマイグレーション（2026-08-14）以前にサインアップしたユーザーは`credit_balances`行が存在せず、`UPDATE`のみの実装だと0件更新で失敗が表面化しないままStripe顧客IDが永久にNULLになる（Billing Portal到達不能＋購入のたびに重複顧客作成）。`20260815120000_fix_stripe_customer_id_upsert.sql`で既存ユーザーへの`credit_balances`行補完＋`set_stripe_customer_id`をupsert化して解消。
4. **ログインレート制限がIP偽装で回避可能**: `X-Forwarded-For`の先頭値はクライアントが自由に詐称できる。Vercelのエッジが上書きする`x-vercel-forwarded-for`を優先するよう修正。
5. **IP不明時に全ユーザーが同一バケットを共有**: `"unknown"`への固定フォールバックが原因で、ヘッダーが取れない環境だと1人の試行回数超過が全員をロックしうる問題。IP不明時はメールベースの制限のみで判定するよう変更。
6. **メール未指定でのServer Action直接呼び出しが500になる**: `formData.get("email") as string`のnullガード漏れ。事前の型チェックを追加。
7. **（低リスク）`refundCredit`自身の例外が元のAIエラーをマスクする可能性**: `refundCredit`呼び出しを個別`try/catch`で囲み、常に元のエラーが伝播するよう保険を追加（`grade`/`question`両ルート）。
