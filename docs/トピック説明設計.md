# トピック説明機能 設計

> 状態: 実装済み（2026-09-02）。README「ロック中」プレースホルダー（➂トピック説明）を実装したもの。意思決定ログとして残す（`料金プラン設計.md`と同じ位置づけ）。
>
> **実装時に設計から変えた点・追加で決めた点**
> - 会話履歴は`topic_sessions.transcript jsonb`ではなく**`topic_turns`テーブル（1ターン1行）**にした。`listening_turns`という同じ問題を解いた先行実装があり、jsonb追記だとread-modify-writeで同時リクエスト時にターンを取りこぼすため
> - **未完了セッションは再開させる**。`start_topic_session`が進行中セッションを見つけたら回数を消費せずそのidを返す。`実装漏れ調査.md`にある絵画ドリルの「リロードで迷子セッション・多重課金」を構造的に防ぐ
> - **AI1の採点結果を`level_estimate`として`updateLevelScore()`に流す**（画像描写ドリルと同じ扱い）。AI5の質問難易度調整にも返ってくる
> - 上限の判定は`topic_monthly_limit()` RPCに集約（`app_config`はSECURITY DEFINER経由でしか読めないため、残り回数の画面表示にもこのRPCを使う）
> - 月の区切りはUTC月初（DBの`date_trunc('month', now())`とTS側の`toISOString()`で一致させている）

## 1. コンセプト（確定）

プロフィール（職業・趣味）に連動してAIが英語で質問し、ユーザーが英語で答える**自由継続の会話**。セッションを終えたタイミングでAI1がまとめて添削し、`weak_points`へ還元する。

README の設計思想（質問する行為の心理コストは常にゼロ、恥は事後の振り返りにだけ乗せる）を会話パートナーにも適用する。**会話中のAI5は訂正・採点を一切しない。**訂正はすべてセッション終了後のAI1に委ねる。会話中に間違いを指摘されると発話がすぐ止まる（Leveltモデルでいう「文法組立」が萎縮する）ため。

## 2. 提供条件（確定）

**全プラン利用可、クレジット消費ではなく月間セッション上限で制御**。Free/Standard/Proいずれも実装する（完全ロックにはしない）。差別化は「回数」と「AI5のモデル品質」の2軸。

| プラン | AI5モデル | 月間セッション上限 |
| --- | --- | --- |
| Free | Sonnet | 2セッション/月 |
| Standard | Sonnet | 8セッション/月 |
| Pro | Opus | 20セッション/月 |

Freeも同じSonnetで動かす（Haiku案は撤回）。モデル品質を落とすと「浅い会話」が製品コンセプトそのものへの第一印象になり、フリーミアムが逆効果になるため。Free/Standardの差は回数のみ、Standard/Proの差は回数＋会話相手の質（Opus）の2段構え。既存のPro差別化軸（添削の深さ／弱点トレンドレポート）に並ぶ**3本目の質的差別化**にもなる。

上限値は`app_config`テーブル（既存）にキーを追加する形で運用時に調整可能にする（`topic_monthly_limit_free` / `_standard` / `_pro`）。

## 3. モデル選定（確定）

会話パートナーは**新設のAI5**として切り出す（既存 AI1〜AI4 の番号を踏襲）。

| 役割 | 既存/新規 | モデル | 理由 |
| --- | --- | --- | --- |
| AI1（採点役） | 既存 `lib/ai1.ts` | Sonnet（プラン問わず固定） | セッション終了時の添削で流用。会話全体トランスクリプトを渡す形に拡張。添削品質はプラン差別化の対象にしない（`weak_points`データの一貫性を優先） |
| AI2（辞書相棒） | 既存 `lib/ai2.ts` | Haiku | 会話中もそのまま併用可（無料・無制限のまま変更なし） |
| **AI5（会話パートナー・新規）** | 新規 `lib/ai5.ts` | **プラン別**：Free/Standard=Sonnet、Pro=Opus | 会話の質がこの機能の価値そのもの。Proだけ一段上のモデルにして「回数」以外の質的な差を作る |

## 4. コスト試算（Opus 5: $5/$25、Sonnet: $3/$15 per MTok換算）

平均セッション＝6往復、最悪ケース＝ソフトキャップの15往復として算出（AI1添削コストはSonnet固定で含む）。

| | 平均セッション原価 | 最悪ケース（15往復）原価 |
| --- | --- | --- |
| Sonnet（Free/Standard） | ≈¥7 | ≈¥16 |
| Opus（Pro） | ≈¥10 | ≈¥24 |

月間上限との掛け合わせ（最悪ケース、既存`grade`クレジットの最悪ケース原価に上乗せ）：

| プラン | 本機能の最悪ケース追加原価 | 既存gradeと合算 | 月額に対する粗利率 |
| --- | --- | --- | --- |
| Free | 2×¥16=¥32/月 | ¥42〜62/月 | (収益源ではないため対象外) |
| Standard | 8×¥16=¥128/月 | ¥331/月（¥980中） | ≈66%（単体79%から低下） |
| Pro | 20×¥24=¥480/月 | ¥953/月（¥1,900中） | ≈50%（単体75%から大きく低下） |

**Proの粗利率50%は意図的なトレードオフとして許容**（Opusを目玉機能にする以上、既存の75%水準からの圧縮は織り込み済み）。まず20セッションで運用開始し、実測後に`app_config`の`topic_monthly_limit_pro`で調整する。合わなければ15セッション（原価¥360、粗利56%）まで下げる選択肢を残す。

## 5. プロフィール要件とゲーティング（確定）

- `profiles.occupation` / `profiles.hobbies` はどちらも `text`、**デフォルトNULL**（サインアップ時は未設定）。既存の`credit_balances.plan is null`＝Freeという判定と同じ「NULL＝未設定」の流儀に揃える
- 設定場所は`/profile`ページ（新規Card、既存の「学年」Cardと同じ構造：テキスト入力2つ＋保存ボタン）。保存は`app/(app)/settings/actions.ts`に新規server action `updateOccupationAndHobbies`を追加（既存`updateGradeBand`と同じ形）
- UI上、未設定時は入力欄のプレースホルダーとして「未設定」を表示
- **ゲーティング**：`occupation`・`hobbies`のどちらかがNULLまたは空文字なら「未設定」扱いとし、トピック説明機能を使わせない
  - `/practice/topic`ページ（サーバーコンポーネント）でプロフィールを取得し未設定なら、`/review`のPro限定トレンドレポートと同じ「ロックカード＋CTA」パターンを流用して「トピック説明を使うには職業・趣味の設定が必要です」＋「プロフィールを設定する」ボタン（`/profile`へのリンク）を表示
  - `POST /api/topic/start`でも同じ判定を防御的に再チェック（未設定なら400）。クライアント側のガードだけに頼らない

## 6. セッションフロー

1. `/practice/topic` 訪問時、プロフィール（occupation/hobbies）判定 → 未設定なら上記のロックカードを表示して終了
2. プラン判定 → 全プラン利用可なのでロック画面は無し。今月の残り回数を表示
3. 「セッションを始める」→ `POST /api/topic/start`
   - プロフィール未設定チェック（サーバー側で再確認）
   - プラン別の月間上限を原子的にチェック＆消費（`consume_credit`と同じ設計パターンのRPC）
   - 上限超過なら429相当で「今月はここまで」表示（アップグレードで回数・モデルが上がる旨を添える）
   - プラン別モデル（Free/Standard=Sonnet、Pro=Opus）でAI5がプロフィールを見て最初の質問を1つ生成
4. チャットUIで往復（AI2辞書相棒パネルも常設で併用可）。`POST /api/topic/message`で1往復ずつ処理し、トランスクリプトをDBに追記
5. 15往復に到達したらAI5が自然に切り上げる一言を返し、以降は入力を無効化して「終了する」のみ表示（ソフトキャップ、ユーザー体験上は「自由に続けられる」を維持しつつコストを保護）
6. ユーザーが「終了して添削してもらう」→ `POST /api/topic/end`
   - AI1が全トランスクリプトを添削（`ai1.ts`のスキーマを拡張、詳細はセクション10）
   - `weak_points`へupsert（`grade/route.ts`と同じロジック）
   - セクション10の会話版結果UIで表示

## 7. データモデル

実装は `supabase/migrations/20260902120000_add_topic_drill.sql`。

- `profiles.occupation` / `profiles.hobbies`（どちらもnullable、NULL＝未設定）
  - **`grant update (display_name, grade_band, occupation, hobbies) on profiles to authenticated;` の再発行が必須**。`20260817190000_add_user_level.sql`でprofilesのUPDATEがカラム単位に絞られているため、これを忘れるとプロフィール保存が42501で落ちる
- `topic_sessions`（1セッション1行。`status`は`active`/`awaiting_end`/`completed`、`ai1_response jsonb`に採点結果を永続化してリロードでも結果を再現）
- `topic_turns`（1ターン1行、`unique (session_id, turn_index)`、`user_id`を非正規化してRLSをフラットに保つ。select/insertのみでターンは不変）
- `topic_session_usage`（`(user_id, usage_month)`複合PK。月初日をキーに含むので**リセット用のcronは不要**）

RPCは3本、いずれもSECURITY DEFINER＋`auth.uid()`ガード：

| RPC | 役割 |
| --- | --- |
| `topic_monthly_limit(p_user_id)` | プラン→`app_config`の上限を引く。画面の残り回数表示にも使う |
| `start_topic_session(p_user_id)` | 進行中セッションがあればそのidを返す（消費なし）→ プロフィール確認 → 上限チェックと加算を`insert ... on conflict ... where session_count < 上限 returning`で原子的に実行 → セッション起票。上限超過はnullを返し、呼び出し元が429に翻訳 |
| `refund_topic_session(p_user_id, p_session_id)` | AI5の初回発話生成に失敗したときの巻き戻し。ターン0件のセッションのみ削除して当月カウンタを1戻す |

## 8. API設計

リスニングドリルと同じ`sessions`系の構成に揃えた（設計時の`/start` `/message` `/end`から変更）。

| エンドポイント | 役割 |
| --- | --- |
| `POST /api/topic/sessions` | プロフィール確認→`start_topic_session`→AI5の初回発話を`turn_index=0`で保存。再開時は`{resumed:true}`を返しAI5を呼ばない。上限超過は429、プロフィール未設定は400 |
| `POST /api/topic/sessions/[id]/turns` | ロックの内側でターンを読み直して`turn_index`を採番→userターン保存→履歴全体でAI5呼び出し→ai5ターン保存。上限到達で`{turnCapReached:true}`＋`awaiting_end`へ |
| `POST /api/topic/sessions/[id]/complete` | AI1が会話全体を採点→`ai1_response`に保存→`weak_points`upsert→`updateLevelScore`をfire-and-forget。採点済みなら保存済み結果を返す（二重採点しない） |

いずれもセッション所有者チェック（`topic_sessions.user_id === auth.uid()`）必須。クレジットは消費しないが、`withConcurrencyLock`は使う（二重送信でターンが競合しないようにするため）。Opusと会話全体の採点は遅くなりうるので3ルートとも`export const maxDuration = 60`。

## 9. AI5プロンプト設計の要点

- 役割：職業・趣味に興味を持って質問してくる会話相手。**訂正・採点はしない**（AI1に委譲）
- 入力：プロフィール（occupation/hobbies）、`level_score`（既存の英語レベル指標で質問の複雑さを調整）、直近のトランスクリプト全体
- 出力：次の発話1つのみ（自由継続なので「会話の終わり」をAI5が決めない設計。終了判断はユーザーの明示アクションかシステムのソフトキャップのみ）

## 10. 添削結果UI（会話版・確定）

`grading-result-card.tsx`は「1つの連続したテキスト」を前提にした構造（`corrected_text`＋その中のフラグメント単位の`errors`）なので、複数ターンの会話にはそのまま流用できない。**新規コンポーネント**として構成するが、フラグメント単位の指摘表示（カテゴリバッジ・訂正差分・言い換え例）は既存の`GradingErrorSchema`／エラーitemのレンダリング部分（`grading-result-card.tsx`122〜197行目）をそのまま使い回せるため、そこは共通コンポーネントとして切り出す。

### スキーマ拡張（`lib/ai1.ts`に追加）

```ts
const UtteranceRating = z.enum(["excellent", "good", "needs_work"]);
// 3段階。LevelLabel(beginner/intermediate/advanced)やリスニングTier表示と揃えた既存の粒度

const TopicUtteranceEvaluationSchema = z.object({
  turn_index: z.number().describe("トランスクリプト内でのユーザー発言の順番(0始まり)"),
  rating: UtteranceRating,
  errors: z.array(GradingErrorSchema)
    .describe("ratingがexcellent以外の場合のみ1件以上。excellentなら空配列"),
});

export const TopicSessionGradingSchema = z.object({
  overall_comment: z.string()
    .describe("会話全体の流れ・自然さ・話題への踏み込み度についての総評"),
  utterances: z.array(TopicUtteranceEvaluationSchema),
});
```

`GradingErrorSchema`（category/grammar_point/user_fragment/corrected_fragment/explanation_ja/levelt_stage/alternative_phrasings）はそのまま再利用。参照範囲が「提出文全体」から「その1発言」に狭まるだけで構造は変わらない。

### UI構成（新規 `topic-session-result-card.tsx`）

1. **総評ブロック**：会話全体の流れについての`overall_comment`を表示（`grading-result-card.tsx`の「総評」ブロックと同じ見た目）
2. **会話ログ再表示**：AI5の質問（左寄せ吹き出し）とユーザーの回答（右寄せ吹き出し）を交互表示
3. 各ユーザー発言の横に3段階の評価バッジ（緑=excellent「素晴らしい」／黄=good「おおむね良い」／赤=needs_work「要改善」）
4. `rating !== "excellent"` の発言の直下に、その発言に対する`errors`一覧を展開表示（カテゴリバッジ・フレーズ比較・解説・言い換え例＝既存の指摘itemレンダリングを共通化して流用）
